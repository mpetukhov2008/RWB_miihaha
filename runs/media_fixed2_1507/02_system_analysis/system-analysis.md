# Системный анализ

## Границы системы
**Внутри:** Модуль распознавания и верификации фотографий (распознавание рекламного блока, оценка качества снимка, сверка с эталонным макетом), Модуль анализа видеопотока и детекции рекламного ролика (поиск временных меток start_time/end_time), Модуль автоматической нарезки видео (вырезание 15-секундного фрагмента, формирование MP4/H.264), Модуль хранения и интеграции результатов (сохранение в S3, отправка статусов в Kafka и REST API), Мобильное приложение (Android/PWA) для загрузки исходных медиафайлов и запуска обработки, Backend-сервис (C#/.NET) для оркестрации обработки и управления заявками
**Снаружи:** Сотрудник технической службы (актор, загружающий файлы и запускающий обработку), Смежная система (принимает итоговые файлы и статусы через Kafka/REST API), S3-хранилище (внешнее хранилище для итоговых медиафайлов), Kafka (внешняя шина событий для передачи статусов), REST API смежной системы (внешний интерфейс для передачи статусов и ссылок)

## Роли и разрешения
- **Сотрудник технической службы**: Загружать исходные фото (JPEG/PNG) и видео (150–300 с) в систему; Загружать эталонный фотомакет (JPEG/PNG) для сверки; Запускать обработку фотоотчета (автоматически или принудительно); Запускать анализ видеопотока и нарезку ролика; Просматривать результаты обработки (статус, процент схожести, временные метки); Получать ссылку на сохраненный итоговый файл
- **Смежная система**: Получать итоговые медиафайлы из S3; Получать статусы выполнения через Kafka (тонкие события); Получать статусы выполнения и ссылки на файлы через REST API; Привязывать результаты к соответствующим заявкам

## Сценарии использования
### US-001: Распознавание и верификация фотоотчета
**Актор:** Сотрудник технической службы
**Требования:** FR-001, NFR-002
**Шаги:**
1. 1. Сотрудник загружает фото рекламной конструкции (JPEG/PNG) и эталонный фотомакет (JPEG/PNG) в мобильное приложение.
1. 2. Мобильное приложение передает файлы в backend-сервис.
1. 3. Backend-сервис запускает модуль распознавания: находит рекламный блок на фото, оценивает качество снимка (фокус, освещенность, блики/засветы).
1. 4. Модуль сверяет фото с эталонным макетом и вычисляет процент схожести.
1. 5. Модуль возвращает один из статусов: «Соответствует макету», «Не соответствует», «Низкое качество».
1. 6. При успешной проверке фото автоматически распределяется и привязывается к заявке.
1. 7. Итоговый файл сохраняется в S3, статус и ссылка передаются в Kafka и REST API смежной системы.
**Результат:** Фотоотчет верифицирован, результат привязан к заявке, смежная система уведомлена о статусе и ссылке на файл.

### US-002: Анализ видеопотока и детекция рекламного ролика
**Актор:** Сотрудник технической службы
**Требования:** FR-002, NFR-001
**Шаги:**
1. 1. Сотрудник загружает видеоролик длительностью 150–300 секунд и эталонный фотомакет (JPEG/PNG) в мобильное приложение.
1. 2. Мобильное приложение передает видео и макет в backend-сервис.
1. 3. Backend-сервис запускает модуль анализа видеопотока: анализирует кадры видео, ищет появление искомого рекламного креатива.
1. 4. Модуль определяет точные временные метки (start_time, end_time) появления креатива в исходном видео.
1. 5. Модуль формирует отчет с временными метками появления креатива.
1. 6. Если обнаружено несколько вхождений, все вхождения фиксируются в отчете (по умолчанию).
**Результат:** Сформирован отчет с временными метками (start_time, end_time) появления целевого рекламного ролика в исходном видео.

### US-003: Автоматическая нарезка видео
**Актор:** Сотрудник технической службы
**Требования:** FR-003, NFR-001
**Шаги:**
1. 1. На основе временных меток из US-002 модуль нарезки запускает FFmpeg для вырезания 15-секундного фрагмента.
1. 2. FFmpeg вырезает ролик по границам start_time и end_time с погрешностью не более 0,1 секунды.
1. 3. Формируется итоговый видеофайл в формате MP4 с кодеком H.264.
1. 4. Итоговый файл автоматически распределяется и привязывается к заявке.
1. 5. Файл сохраняется в S3, статус и ссылка передаются в Kafka и REST API смежной системы.
**Результат:** Вырезан 15-секундный рекламный ролик (MP4/H.264), привязан к заявке, смежная система уведомлена.

### US-004: Хранение и интеграция результатов
**Актор:** Смежная система
**Требования:** FR-004
**Шаги:**
1. 1. После успешной обработки фото (US-001) или видео (US-003) модуль хранения выгружает итоговый файл в S3 через endpoint S3.
1. 2. Модуль формирует событие со статусом «Выполнено» и ссылкой на сохраненный файл (или его ID).
1. 3. Событие публикуется в Kafka (тонкие события).
1. 4. Статус и ссылка передаются через методы REST API смежной системы.
1. 5. Смежная система принимает файлы и статусы, привязывает результаты к заявкам.
**Результат:** Итоговые медиафайлы сохранены в S3, смежная система получила статусы и ссылки через Kafka и REST API.

## Сущности
- **Заявка** — Бизнес-объект, к которому привязываются результаты обработки фото и видео. Идентифицирует конкретную рекламную конструкцию и задачу.
- **Фотоотчет** — Исходное фото рекламной конструкции (JPEG/PNG), загруженное сотрудником. Подлежит распознаванию, оценке качества и верификации по эталонному макету.
- **Эталонный макет** — Статический шаблон (JPEG/PNG), используемый как референс для сверки фото и видео. Является входным параметром для модулей распознавания и детекции.
- **Видеопоток** — Исходный видеоролик длительностью 150–300 секунд, загруженный сотрудником. Подлежит анализу для детекции целевого рекламного ролика.
- **Целевой ролик** — Вырезанный 15-секундный рекламный фрагмент (MP4/H.264), сформированный по временным меткам из анализа видеопотока.
- **Отчет о детекции** — Результат анализа видеопотока: временные метки (start_time, end_time) появления целевого креатива в исходном видео. Может содержать несколько вхождений.
- **Результат обработки** — Итоговый артефакт: статус (Соответствует/Не соответствует/Низкое качество/Выполнено), процент схожести, ссылка на файл в S3, ID файла. Передается смежной системе.
- **Событие Kafka** — Тонкое событие, публикуемое в Kafka со статусом выполнения и ссылкой на сохраненный файл. Используется для асинхронного уведомления смежной системы.

## Допущения
- Хронометраж одного целевого рекламного ролика фиксирован и составляет 15 секунд.
- Сотрудник загружает исходные файлы после съемки в зоне со стабильным интернет-соединением для передачи тяжелых видео в S3/на бэкенд.
- Эталонный статический макет (JPEG/PNG) является единственным референсом как для фото, так и для видео.
- Обработка видео длительностью 150 секунд укладывается в 20 минут при штатной нагрузке.
- При обнаружении нескольких вхождений целевого ролика в видео вырезаются все вхождения (по умолчанию из open_questions Q-002).
- Ключевые элементы макета распознаваемы на протяжении ролика или фиксируются по стартовому/финальному кадру с отсечкой 15 секунд (по умолчанию из open_questions Q-001).
- Мобильное приложение (Android/PWA) является единственным клиентским интерфейсом для загрузки файлов и запуска обработки.
- Backend-сервис (C#/.NET) оркестрирует все модули обработки и управляет заявками.
- S3 используется как единственное хранилище для итоговых медиафайлов.
- Kafka и REST API используются параллельно для передачи статусов смежной системе.

## Открытые вопросы
- Q-001: Должен ли эталонный статический макет присутствовать на протяжении всех 15 секунд видеоролика, или ролик динамический и макет появляется только в ключевых кадрах? (Влияние: architecture. По умолчанию: ключевые элементы макета распознаваемы на протяжении ролика или фиксируются по стартовому/финальному кадру с отсечкой 15 секунд.)
- Q-002: Если в 300-секундном видео обнаружено несколько вхождений искомого ролика, нужно ли вырезать все вхождения или только первое? (Влияние: other. По умолчанию: вырезаются все найденные целевые ролики с указанием всех временных меток в отчете.)
